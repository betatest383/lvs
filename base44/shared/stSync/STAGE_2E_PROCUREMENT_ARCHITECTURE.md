## 0. ARCHITECTURAL GOVERNANCE

The following principles govern every procurement entity, synchronization workflow, and future ServiceTitan integration. These principles take precedence over individual implementation decisions unless explicitly superseded by owner approval.

### 0.1 System of Record

ServiceTitan remains the external procurement and accounting source for synchronized procurement entities.

LVC OS is the operational system of workflow record.

Synchronization exists to maintain data consistency between systems — it does not control operational execution.

ServiceTitan synchronization may create or update only ServiceTitan-owned fields. Synchronization must never overwrite LVC OS operational data.

The following remain exclusively LVC OS-owned:

- workflow state
- workflow history
- approval state
- approval history
- AI recommendations
- AI-generated guidance
- technician actions
- warehouse actions
- assigned tasks
- task responses
- notifications
- exception workflows
- evidence
- photos
- attachments
- KPI history
- operational audit history
- coaching history
- inventory investigation history
- internal notes
- operational comments
- root-cause analysis
- warehouse verification records
- physical verification records

If ServiceTitan and LVC OS contain different values for an LVC-owned field, synchronization must preserve the LVC OS value. Synchronization updates ServiceTitan-owned data only. LVC OS remains the authoritative operational workflow platform.

### 0.3 Schema Promotion Rule

No ServiceTitan field may be promoted from `servicetitan_raw_data` into a first-class schema field unless it satisfies at least one of the following:

1. **Immutable identity** — the field is a permanent external identity key used for record matching
2. **Synchronization integrity** — the field is required for conflict detection, stale-event protection, or dependency resolution
3. **Operational workflow** — an LVC OS workflow actively reads, filters, or branches on this field
4. **Reporting requirement** — a defined LVC report aggregates or filters by this field
5. **Audit requirement** — a defined LVC audit process queries or displays this field for compliance traceability
6. **Owner-approved display requirement** — the owner has explicitly approved this field for user-facing display

If none of these criteria are met, the field shall remain inside `servicetitan_raw_data`.

This rule applies to every future synchronization domain — Purchase Orders, Receipts, Bills, Transfers, Inventory Adjustments, and any domain added after Stage 2E.

Enforcement: every schema field proposed for promotion must cite the specific criterion satisfied and the workflow/report/audit that depends on it. Proposals that cannot cite a dependent workflow are rejected.

### 0.4 Warehouse Operational Ownership

Synchronization imports procurement documents. Operational execution belongs exclusively to LVC OS.

The procurement synchronization layer represents external business events. LVC OS controls operational execution after those events arrive.

The following warehouse processes remain LVC OS-owned:

- replenishment generation
- replenishment approval
- replenishment prioritization
- warehouse picking
- pick confirmation
- staging
- truck loading
- truck unloading
- truck receiving
- truck returns
- warehouse returns
- truck-to-truck transfers
- warehouse-to-truck transfers
- warehouse-to-warehouse transfers
- technician material requests
- emergency material requests
- inventory counts
- cycle counts
- variance investigations
- damaged material workflow
- waste material workflow
- shortage workflow
- overflow return workflow
- exception resolution
- warehouse approvals
- technician confirmations
- manager review
- AI warehouse recommendations
- warehouse KPIs
- inventory coaching workflows

Synchronization must never overwrite operational workflow decisions performed inside LVC OS. ServiceTitan reflects procurement events. LVC OS governs operational execution.

Inventory ledger movements generated by LVC OS workflows remain authoritative unless an owner-approved reconciliation process explicitly determines otherwise.

## 1. COMPLETE PROCUREMENT ARCHITECTURE

### 1.1 Design Principles

Stage 2E inherits the proven synchronization architecture established during Stages 2A–2D:

- **Immutable Identity Matching** — Every record matched exclusively by its ServiceTitan ID. Never by name, number, or description.
- **Shared Synchronization Engine** — All domains route through `stSyncEngine.runSyncEngine()` and `safeCreateWithRecheck()`.
- **Field Ownership Contract** — ServiceTitan-owned fields overwrite local values; LVC-owned fields are protected.
- **Three-Status Separation** — Every procurement entity maintains three independent status fields: (1) ST-owned source lifecycle status (`status`), (2) LVC-owned workflow status (`lvc_workflow_status`), (3) synchronization status (`servicetitan_sync_status`). These are never combined. Sync overwrites `status` but never touches `lvc_workflow_status`.
- **Header-First Synchronization** — Headers may arrive before lines (separate endpoints, pagination, delayed dependencies). Header identity and valid header data are sufficient to create the header. Line-fetch or line-dependency failures do NOT invalidate headers. `lines_sync_status` (not_started, pending, partial, complete, failed) tracks line-level completeness. Headers remain eligible for line retry.
- **Dependency Graph Enforcement** — Domains defer (not fail) when dependencies are unresolved.
- **Watermark-Based Incremental Sync** — Each domain has its own watermark for resumable, bounded processing.
- **Retry Protection** — Bounded concurrency, exponential backoff, rate-limit detection, and post-create recheck.
- **Diagnostic Observability** — Every domain exposes retry metrics, dependency status, reconciliation, and integrity checks.

## 4. WATERMARK STRATEGY

### 4.1 Per-Domain Watermarks

Each domain has a dedicated watermark entity tracking:

| Field | Description |
|---|---|
| `watermark_key` | Unique per (tenant, environment) |
| `activation_timestamp` | Go-live timestamp — records before this are pre-activation |
| `last_modified_scan_at` | High-water mark for `modifiedOnOrAfter` cursor |
| `recovery_window_start/end` | Current recovery window boundaries |
| `recovery_window_status` | `idle` / `in_progress` / `completed` / `failed` |
| `recovery_overlap_minutes` | Overlap safety margin (default 5 min) |
| Domain counters | `*_imported_since_activation`, `*_updated`, `*_deferred_*` |
| `backfill_status` | `never_started` / `confirmed` / `in_progress` / `completed` |

### 4.2 Watermark Entities

| Domain | Watermark Entity |
|---|---|
| Purchase Order | `PurchaseOrderSyncWatermark` |
| Receipt | `ReceiptSyncWatermark` |
| Bill | `BillSyncWatermark` |
| Transfer | `TransferSyncWatermark` |
| Inventory Adjustment | `InventoryAdjustmentSyncWatermark` |

### 4.3 Activation Protocol

1. Owner calls `mode=activate` → creates watermark with `activation_timestamp = now`
2. Zero records imported during activation
3. Subsequent `incremental` / `controlled_batch` / `bounded_retry` modes process records
4. Watermark advances `last_modified_scan_at` only after a full recovery window completes successfully

## 5. RETRY STRATEGY

### 5.1 Shared Infrastructure

All procurement domains inherit the retry protection from `stRateLimitProtection.ts`:

| Mechanism | Implementation |
|---|---|
| Rate-limit detection | `isRateLimitError()` — HTTP 429, Base44 rate-limit response |
| Retriable detection | `isRetriableError()` — network, timeout, 5xx |
| Exponential backoff | `withRetry()` with jitter and `Retry-After` header extraction |
| Bounded concurrency | `runBoundedConcurrent()` — max 3–5 concurrent operations |
| Safe create | `safeCreateWithRecheck()` — post-create recheck prevents duplicates |
| Retry metrics | `SyncRetryMetrics` — `lookup_retries`, `create_retries`, `update_retries` |

### 5.2 Domain-Specific Retry Behavior

| Operation | Retry Policy | Max Retries |
|---|---|---|
| Dependency lookup (Vendor, Material, PO) | Bounded with backoff | 5 |
| Record create | Safe create with recheck | 5 |
| Record update | Bounded with backoff | 5 |
| Page fetch | Bounded with backoff | 3 per page |

### 5.3 Deferred Records

When a dependency cannot be resolved:
1. Record is marked `deferred` (not `failed`)
2. A `DeferredDependentRecord` is created tracking the unresolved dependency
3. The record is retried in the next sync cycle
4. If the dependency is never resolved, the record remains deferred indefinitely (never permanently failed)

## 8. HISTORICAL IMPORT PLAN

### 8.1 Authorization Gate

No domain proceeds to historical import until ALL acceptance criteria pass. Historical import is authorized by:

1. Owner calls `mode=activate` → watermark established
2. Owner runs `mode=dry_run` → review report
3. Owner runs `mode=controlled_batch` (250 records) → review results
4. Owner runs `mode=rerun_verification` → idempotency confirmed
5. Owner reviews acceptance checklist
6. Owner sets `backfill_status=confirmed` via watermark update
7. Bounded historical batches begin (250 records per batch, resumable)

### 8.2 Batch Strategy

| Parameter | Value |
|---|---|
| Batch size | 250 records (max) |
| Concurrency | 3–5 workers |
| Max retries per record | 5 |
| Overlap window | 5 minutes |
| Runtime limit | 540 seconds (9 minutes) per batch |
| Watermark advancement | Only after full batch completes successfully |

### 8.3 Resumption Protocol

If a batch stops (rate limit, runtime limit, page limit):
- Watermark NOT advanced
- Next batch re-fetches from the same window
- Already-created records detected as `unchanged`
- Processing continues from where it stopped

## 10. RISK ASSESSMENT

### 10.1 High Risk

| Risk | Mitigation |
|---|---|
| **API endpoint uncertainty** — ServiceTitan Procurement API paths are estimated. Live `verify_api_modified_on` must confirm before any writes. | All configs marked "to be verified." Zero writes until API connectivity confirmed. |
| **Line-level identity** — ServiceTitan may not expose stable line-level IDs for PO lines, receipt lines, bill lines, transfer lines. | Line adapters must extract the most stable available identifier. If no line ID exists, composite key (parent_id + sort_order) is used as fallback with documented risk. |
| **Receipt ledger posting** — Receipts increase warehouse inventory. Incorrect posting could corrupt the inventory ledger. | Receipt sync creates `Receipt` records but does NOT auto-post ledger entries. LVC posts ledger entries through a separate local workflow step after receipt verification. |

### 10.2 Medium Risk

| Risk | Mitigation |
|---|---|
| **Partial receipt complexity** — Multiple receipts per PO with varying line quantities. | Each receipt is a separate record linked to the PO. PO `quantity_received` is updated by ST sync (ST-owned field). LVC tracks receipt state independently. |
| **Bill-Receipt-PO triangle** — One bill from multiple receipts, multiple bills from one PO. | Bill references both PO and Receipt by immutable ST IDs. Bill lines link to receipt lines and PO lines individually. |
| **Transfer warehouse resolution** — Transfers reference source + destination warehouses. Both must resolve to local WarehouseLocation records. | Transfer adapter resolves both source and destination by `servicetitan_warehouse_id`. If either is missing, the transfer is deferred. |
| **Inventory adjustment read-only enforcement** — ST adjustments must NOT overwrite LVC inventory quantities. | Adjustment sync creates `InventoryAdjustment` records with ST-owned snapshot fields. LVC's `ledger_posted` flag is independent. ST adjustments never call the inventory ledger. |

### 10.3 Low Risk

| Risk | Mitigation |
|---|---|
| **Rate limiting** — Procurement API may have stricter rate limits than CRM/Pricebook. | Bounded concurrency (3–5), exponential backoff, `Retry-After` handling — all inherited from Stage 2D. |
| **Duplicate creation** — Concurrent batch retries could create duplicates. | `safeCreateWithRecheck` enforced universally through `stSyncEngine` refactoring (Stage 2D). |
| **Stale events** — Out-of-order webhook delivery. | `compareSourceVersions` stale-event protection inherited from Stage 2D. |
